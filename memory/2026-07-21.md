## IEEE匹配率分析（小米0627 + 海信0709）

### 背景
小胡在群里发起IEEE匹配率分析需求。数据来自技术侧吴坤城跑的4种加密方式匹配结果。
- 小米0627：caid=4142538，spid=31nGx/31lHe，活动名「智屏视界_FY2526_像素方案_直投BB_P&G【测】」
- 海信0709：caid=4143171~4143174，每个活动2个spid（a/b, c/d, e/f, g/h），活动名「智屏视界_FY2627_像素方案_IB/BB_P&G【测】」
- 广告主：P&G，代理：Starcom PG
- 海信4个活动方案交叉：IB方案/BB方案 × IB辅助/BB辅助

### 点位与品牌对应（AdMonitor拉取）
- a/c/e/g组 = SAFEGUARD（舒肤佳），视频前贴片
- b/d/f/h组 = BRAUN（博朗），视频前贴片
- 每个活动下还有31vv*系列辅助spid（无数据）

### 匹配率汇总
- 小米31nGx：100%（57360/57360，含81个带冒号小写增量）
- 小米31lHe：99.94%
- 海信SAFEGUARD(a/c/e/g)：99.99%
- 海信BRAUN(b/d/f/h)：98.89%（每spid差500+）

### 4种加密方式说明
1. 去冒号大写（正规加密）：m6a对应的加密方式，主匹配
2. 去冒号小写：纯数字MAC时=去冒号大写（重复）
3. 带冒号大写：m6对应的加密方式，纯数字MAC重复
4. 带冒号小写：少数增量匹配
- 纯数字MAC：去冒号后大写=小写，导致方式2/3重复
- 小米31nGx有247个纯数字MAC（千分之4.3）

### 关键发现
1. 海信b/d/f/h组（BRAUN）未匹配率1.11%，是a/c/e/g组（SAFEGUARD）0.01%的100倍
2. 两组TVM投放量级几乎相同，但触达设备几乎零交集（19737个UUID仅16个重叠）
3. 未匹配UUID（SmartTV 595个）与匹配上的UUID在所有字段结构上完全一致（uuid=m6a=m6b，全32位MD5，全m=12，全SmartTV）
4. no_match.txt里混入了VIDAA_TV设备（169个UUID），属于其他活动的副产品，非海信0709数据
5. MD5不可逆，无法从加密值反推原始MAC的OUI
6. 未匹配设备的Build型号在匹配上的设备中也大量存在，无特异性
7. 未匹配UUID的曝光频次分布与匹配上的接近，无异常高频刷量特征

### 踩坑记录
1. **误判m6b为非MAC**：看到m6b是32位就推断"不是MAC而是设备UUID"，被小胡纠正——m6b是MAC的MD5，32位是加密后正常长度
2. **误判m字段=SDK类型**：把m字段直接等同于SDK类型（m=10→爱奇艺SDK，m=12→秒针SDK），无依据。m是媒体ID不是SDK类型
3. **OUI查询责任方归错**：把秒针内部的OUI查询错误归给了海信侧。OUI查询是秒针内部技术的事，海信要排查的是像素方案回传日志过少
4. **no_match.txt未分类**：一开始把596个UUID都当海信0709数据分析，后来发现混入了VIDAA_TV设备（其他活动副产品），实际海信0709未匹配是595个SmartTV UUID

### 踩坑根因分析
四个错误根子相同：**用模式匹配代替了事实确认**
- 看到32位→想到UUID→跳到"不是MAC"，跳过了查字段定义
- 看到ua里有QIYIVideo→脑补SDK类型，没有确认m字段定义
- 看到"技术查"→归到"媒体/技术侧"大桶，没有区分秒针内部还是媒体侧
- 拿到no_match.txt→默认全是目标活动数据，没有先检查数据范围

**教训：先确认事实，再做推断。不用经验跳跃代替定义查证。**

### 字段知识
小胡提供了AdMonitor字段与宏参数注册表（PDF），已存到 `knowledge/adm-fields-reference.md` 和 `knowledge/adm-fields-reference.txt`
- m6 = 保留冒号大写MAC的MD5
- m6a = 去冒号大写MAC的MD5
- m6b = OTT有线MAC（去冒号大写）的MD5
- m6c = OTT无线MAC（去冒号大写）的MD5
- m6d = OTT蓝牙MAC（去冒号大写）的MD5
- uuid = 最终用户唯一标识，idfrom = uuid判定来源
- ⚠️ 高度保密不对外

### 结论：MAC不在IEEE库 ≠ 异常流量
- 多种可能：IEEE库版本问题、本地管理MAC、未注册OUI、虚拟MAC等
- 小胡判断：各组之间差异不大（1%以内），不像大规模异常流量
- AdMonitor补充：IVT规则里没有"MAC不在IEEE库"这条，系统判异常看行为模式不是设备标识注册状态
- 1.11%未匹配率不算高，未匹配设备字段结构与正常设备一致，无刷量特征
