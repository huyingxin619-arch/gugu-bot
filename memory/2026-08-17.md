### 最终工作流（小胡确认，8/17更新）

关键点：不依赖本地文件互访，用 Octo 在线文档作为信息传递媒介。背景文件是理解前因后果的必要输入，每个会议都要问小胡要。

### octo-cli 文档读取能力
- `octo-cli docs content get <docId> --bot-id guguhyx_bot` 可读 Octo 在线文档内容
- 需要先 `octo-cli auth login` 建好 bot 的 auth profile（已完成）
- 文档权限由文档创建者通过 `octo-cli docs forward-grant` 授予 reader/writer
- octic 已给 guguhyx_bot 授了 10 份会议文档的 reader 权限
- 文档内容返回 JSON block 结构（ProseMirror/Tiptap 格式），需解析
- `octo-cli docs export <docId> --export-format md -o <path>` 可导出为 markdown

### Octo 群信息查询
- 被问到群名/群信息时，用 `octo-cli` 或 Octo Bot API `GET /v1/bot/groups/:group_no` 查真实群名
- 不要依赖 inbound context 里的 `group_subject`（那是原始群ID）

### 踩坑
- 被问"群名是什么"时直接报了 inbound context 里的 `group_subject`（原始群ID），没去查真实群名。octic 是主动调 `octo_management` 的 group-info 接口查的
- 根因：Octo 插件 inbound.js 里 `GroupSubject` 直接赋的是 `message.channel_id`，没解析群名。这是插件层面的 bug
- 教训：被问到群信息时，主动调 Octo Bot API 查真实群名，不依赖 inbound context
