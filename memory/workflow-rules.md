# 周报/写作规范

## 周报写作

- **所有进行中的项目都要列**，不能只选"今天提到的"
- **有实质进展的项目**：写清楚做了什么、结论是什么
- **无实质进展的项目**：只列当前状态，一行带过
- **一次性咨询/内部工具配置不列**：如当妮录屏、上汽大众、OKR安装等
- **细节适度精简**：对外周报不展开排查细节（如UA排查8条证据、ID Landscape具体数据），一行标题带过即可
- **发出前自检三条：**
  1. 无具体人名（包括内部同事名字）
  2. 无具体报价/金额数字
  3. 客户名只有宝洁类 KA 客户需脱敏，三九等其他客户可正常写

## 每日备份前扫描（凌晨3点 cron 执行前）

扫描当日 `memory/YYYY-MM-DD.md`，按内容性质提炼：

| 内容类型 | 动作 |
|----------|------|
| 新的长期事实 | 写入专项文件 + 更新 MEMORY.md 索引 |
| 认知误区/本能校准 | 提炼到 SOUL.md |
| 操作规则 | 提炼到 AGENTS.md |
| 可复用知识 | 提炼到 knowledge/ |
| 具体踩坑 | 留日记，判断是否有普遍性 |

## 会议消化分类体系（5类）

消化会议内容时按以下5类分类输出，不混在一起：
1. **项目进展** — 项目状态变化、测试结果、数据指标变化。回答"事情到哪了"
2. **决策记录** — 方案选择/否掉，以及为什么。回答"为什么走这条路不走那条"
3. **知识补充** — 跨项目的技术概念、行业机制、方法论。回答"这东西怎么运作的"
4. **背景/人** — 人物变动、对接关系、组织变化。回答"谁负责什么、谁是谁"
5. **待办** — 谁做什么什么时候交。回答"接下来干什么"

## 会议消化流程（🦞开会群）

### 角色分工
- **octic**：会后处理录音 → 转写/纪要/待办落盘到 Octo 在线文档 → 给 guguhyx_bot 授 reader 权限 → 群里 @古古 给文档链接
- **古古**：读原文 → 问小胡要背景文件 → 结合文件+原文+项目认知做分析 → 认知不一致发群里让小胡判断 → 小胡判完后更新项目文件
- **小胡**：提供背景文件 → 判断认知分歧 → 拍板结论

### 古古消化步骤（必须按顺序）
1. **读原文** — 用 `octo-cli docs content get <docId> --bot-id guguhyx_bot` 读取纠错文本和总结，不依赖概要或转述
2. **确认人名** — 纪要里的人名跟实际对应关系必须跟小胡确认，不假设（2026-08-18教训：新宇≠心宇，应欣=胡映昕）
3. **问背景文件** — 每个会议都要问小胡有没有相关文件（测试报告、方案文档、数据包等）
4. **做分析** — 结合文件+原文+项目认知，逐条分析
5. **列疑问** — 认知不一致的发群里让小胡判断，不自己下结论
6. **等小胡拍板** — 小胡判完后才更新项目文件
7. **落盘** — 更新项目文件 + 当日日记，提炼到对应专项文件
8. **同步octic** — 小胡纠正的人名/认知错误、以及古古与octic认知不一致经小胡拍板的结论，古古同步给octic，octic更新自己的context以提升转录准确性

### 认知同步机制（双向）
- **小胡纠正古古** → 古古改完自己的文件后，同步给octic
- **古古发现octic纪要里有认知不一致** → 发群里让小胡判断 → 小胡拍板后古古和octic双方共同更新
- 同步方式：在群里@octic说明纠正内容，octic确认收到并更新

### 分析纪律（绑定到具体动作，不可跳过）
- 做对照分析时，必须逐条确认"会议讨论的问题"和"配置表中的规则"是否指向同一件事，不能因为名称相似就关联
- 看到"两种可能"时不能收敛成"一种结论"，必须如实呈现待排查状态
- 基于配置文件做对照分析时，先回答：这个关联有没有经过事实确认？是否存在名称相似但实际无关的可能？

### 文档链接验证
- octic 发文档链接前，确认 docId 对应的录音时间与会议日期一致
- 古古读到文档后，先核对录音时间，发现与会议日期不符立即在群里提出

### 日期标注规则
- 日记和项目文件中，标注的是会议实际日期（录音日期），不是文档创建/发送日期

### 关键点
- 不依赖本地文件互访，用 Octo 在线文档作为信息传递媒介
- 背景文件是理解前因后果的必要输入，每个会议都要问小胡要
- 不在群里贴文档全文，用在线文档链接传递信息
- 落盘前必须走完"读原文→确认人名→问背景文件→做分析→列疑问→等拍板"六步

## 梳理/汇报输出标准

当被要求梳理情况、总结事件、列TODO时：

1. **不当压缩器** — 不复述别人已说过的内容，只加增量价值
2. **结构必须完整** — 起因→排查过程→修复结果→遗留问题，不是流水账
3. **每条带细节** — 不只说"plist串配置"，说清楚串到哪、后果是什么、怎么修的
4. **TODO分优先级并给理由** — 🔴高/🟡中/🟢低，每条说明为什么这个优先级
5. **有补充发现** — 在别人说的之外，自己找到新问题或新视角
6. **有自己的判断** — 哪些是真问题、哪些可以后面再说，给出自己的意见

反面案例：2026-07-24，小胡要求梳理当天排查情况，输出只有阿德内容的缩水版复述，无增量信息、无结构、无细节、无优先级。

## 项目 vs 知识分层

- **项目** = 有起止、有负责人、有状态 → `projects/`
- **知识** = 可跨项目复用的原理、架构、术语 → `knowledge/`
