## 一、背景与目标

### 1.1 为什么需要抽样

像素监测方案中，媒体每次曝光请求都会向秒针CF服务请求挑战因子。如果全量下发CF，媒体全量截屏取帧回传，再全量送CMP比对，成本过高（CMP单节点12-13帧/秒）。

因此需要在**CF下发环节做比例抽样**：媒体请求到达秒针时，按预设比例判断是否给该请求下发CF。被抽中的请求才下发CF→媒体截屏取帧→回传像素指纹→送CMP比对。未被抽中的请求正常走常规监测流程，不触发像素监测。

### 1.2 方案演进说明

方案经过多轮讨论演进，以下为关键节点：

| 时间 | 讨论内容 | 结论 |
|------|---------|------|
| 8/18-8/19 | 讨论是否在CF接口侧抽样 | 当时认为不可行：接口无状态无法均衡配额、设备边界未知、开机批量打破均衡；倾向于全量回传后秒针侧抽样 |
| 8/26 | 与Darin对齐抽样策略 | 确定混合抽样：固定比例+底线补齐；Darin希望优先spid级 |
| 8/27 | 内部碰头会落实参数 | 确认在CF下发环节做比例抽样（服务器抽签逻辑）；用比例随机数解决均衡问题；8/19的顾虑部分被解决，部分转为待确认项 |

> **注意**：8/19讨论的"不在CF接口侧抽样"的结论已被8/26-8/27的方案演进覆盖。当前方案就是在CF下发环节做比例抽样。

### 1.3 已确认的约束

- 客户最初与三方和媒体约定了抽样方式（考虑了媒体接受度和算力）
- 媒体侧全量请求CF（秒针按比例决定是否下发，未下发的请求不触发像素监测）
- 小米+海信共约200万设备，月约1亿曝光

## 二、抽样策略：比例抽样 + 底线补齐

### 2.1 核心公式

```
抽样比例 = max(最低样本量 / 预期曝光量, 基础抽样比例)
```

- **最低样本量**：每个spid × creative × 活动周期内至少5000个样本（保证时间均匀性）
- **基础抽样比例**：一个预设的低比例（如1%），量大时按比例抽，量小时补齐到底线
- **上限不封顶**：超过最低样本量的部分多抽无害，只增加CMP成本，不影响准确性

### 2.2 为什么是比例抽样而不是固定数量

| 方案 | 问题 |
|------|------|
| 固定数量（先到先得） | 24小时内严重不均匀——凌晨流量低时抽满，白天高峰全被截掉 |
| 固定数量（随机抽取） | 需要知道当天总量才能算比例，但无法提前知道；且总量不均匀时时间分布会偏 |
| 纯比例抽样 | 量小时样本不足，无法保证均匀性 |
| **比例+底线补齐** | 量大按比例抽（省成本），量小补齐到底线（保证质量） |

### 2.3 服务器抽签逻辑

每次媒体请求到达秒针CF服务时：
1. 识别该请求对应的spid（和creative，如果能携带）
2. 查询该spid对应的抽样比例
3. 生成一个[0,1)随机数
4. 若随机数 < 抽样比例，则下发CF（该请求被抽中）
5. 否则正常走常规监测，不触发像素监测

**此方式解决了8/19讨论的"接口无状态无法均衡配额"问题**：每次请求独立判断，不需要记录历史状态，概率上自然均衡。

### 2.4 抽样颗粒度

```
by spid × by creative × by 活动周期
```

- 分母（预期曝光量）只到spid级别
- 分子 = 5000 × 该spid下creative数量（假设creative内分布与实际一致）
- by day不是强制附加：整个活动周期内样本量够即可，不强制每天达到5000
- 但分母需要按天计算抽样比例（见下方「分母处理」）

## 三、核心参数定义

### 3.1 最低样本量

| 参数 | 值 | 说明 |
|------|-----|------|
| 基础样本量 | 1000/点位/creative/活动周期 | 保证抽样结果与总体分布一致，但不保证时间均匀 |
| 时间均匀样本量 | 5000/点位/creative/活动周期 | 保证15秒内每秒的偏移量分布均匀 |
| 防伪随机数均匀 | ~10000样本 | 65535个随机数值，实际偏移量只落0~7，1万样本即可保证偏移均匀 |

**采用5000作为底线**：兼顾时间均匀性和实际可操作性。

> ⚠️ 待确认：8/26与Darin对齐时底线为1100，8/27内部讨论调整为5000。需确认用哪个口径与Darin沟通。

### 3.2 关于65535随机数的澄清

- CF下发的随机数为两字节（0~65535），用于计算取帧秒数和桶偏移量
- 偏移量实际只落在0~7（3 bit），因此不需要65535个值都出现
- 约1万样本即可保证0~7均匀分布
- **不需要6万多样本**——此前"6万多"是指随机数值域，不是所需样本量

### 3.3 误差控制

| 样本量 | 相对误差 | 说明 |
|--------|---------|------|
| 100 | ±8.5% | 极端少，仅参考 |
| 1000 | ±2.7% | 基本可用，不保证时间均匀 |
| 5000 | ±1.2% | 保证时间均匀 |
| 10000 | ±0.9% | 防伪随机数均匀 |

> 误差由样本量决定，与总体无关（统计学基本定理）。

## 四、分母（预期曝光量）的获取与处理

### 4.1 现状

- 媒体和客户只能提供**活动周期内spid级别的总量**
- 无法提供by day的预估曝光量
- 无法提供by creative的预估曝光量
- creative之间的流量分配比例未知

### 4.2 分母获取方案

```
分母（spid日均预期曝光量）= spid活动周期总曝光量 / 活动天数
```

**为什么用平均分摊而不是历史数据预测：**
- 每月投放节奏、媒体库存不同，历史数据预测性差
- 平均分摊简单透明，易于与客户和媒体对齐
- 即使实际分布不均匀，比例抽样本身能保证抽样结果与实际分布一致

### 4.3 creative级别的处理

- 分母只到spid级别
- 分子 = 5000 × 该spid下creative数量
- **假设**：spid内creative分布与实际流量分配一致
- **保证**：抽样结果中各creative的占比与实际曝光占比一致（如实际5:4:3，抽样也是5:4:3）
- **不保证**：单个creative内的时间均匀性（当该creative曝光量<5000时）

### 4.4 需要CMP/媒体侧提供的信息

- [ ] 每个spid下有哪些creative ID
- [ ] spid活动周期总曝光量（历史数据，用于推算抽样比例）
- [ ] 排期信息（活动起止日期）

## 五、时间均匀性保证

### 5.1 均匀性要求

| 维度 | 要求 | 说明 |
|------|------|------|
| 15秒内每秒分布 | 均匀 | 核心要求——保证各秒采样点不偏 |
| 0~7桶偏移量 | 偏了即可，不要求严格均匀 | 防伪用途，非统计用途 |
| by day分布 | 不强制 | 整个活动周期内够5000即可 |

### 5.2 保底逻辑

当某个spid×creative的实际曝光量达不到5000时：
1. 按实际最大比例抽样（甚至全量下发CF）
2. 告知客户该creative样本量不足，误差范围相应增大
3. 由客户决定是否接受该精度

## 六、特殊场景处理

### 6.1 小米开机广告

**问题**：小米开机的请求≠真实曝光，部分请求不构成实际播放。请求量远大于实际曝光量，如果按正常比例抽样，实际有效样本会严重不足。

**处理方案**：
- 提高抽样比例（高于基础比例，如15%+）
- 具体比例需向小米咨询历史经验：请求中实际构成曝光的比例是多少
- 用实际曝光比例倒推：抽样比例 = 5000 / (预期请求量 × 实际曝光率)

### 6.2 设备支持边界问题（8/19遗留）

8/19讨论时提出"设备池边界未知"——媒体请求CF的设备是否都支持像素方案？

当前处理：
- 需确认媒体在请求时是否默认支持像素监测
- 如果不支持像素方案的设备也来请求CF，抽样比例需要相应打buffer（思源提到的"打8分"）
- 小胡建议：不打buffer，直接让媒体确认支持设备范围

### 6.3 海信

- 当前已知设备覆盖约200万（仅限一个芯片型号）
- session ID回传率仍偏低（8/12批次约50%），但这是SDK适配问题，不影响抽样方案设计
- 抽样方案基于回传成功的有效数据执行

### 6.4 creative ID获取

- 直投活动（非程序化）：creative ID由CMP下发时携带，需确认媒体请求CF时能否带上creative_id
- 小米开机异步过程能否携带creative_id未确认，需与媒体沟通
- Darin希望抽样做到spid级（资源允许时优先）

## 七、CMP交互量级评估

### 7.1 估算框架

因为抽样发生在CF下发环节，被抽中的请求才会触发后续截屏→回传→CMP比对链路，所以：

```
CMP日均交互量 = Σ(各spid日均抽样量) × 帧数/请求 × CMP交互次数/帧
```

- 各spid日均抽样量 = max(5000 × creative数 / 活动天数, spid日均曝光量 × 抽样比例)
- 每个被抽中请求产生的帧数：1-1首帧 + 1-2尾帧 = 2帧（15秒视频）
- 每帧送CMP比对1次

### 7.2 待填入实际数据

> ⚠️ 以下需要历史曝光数据填入：
> - 海信历史spid最低曝光量（活动周期内）
> - 小米历史spid最低曝光量（活动周期内）
> - 各spid下creative数量
> - 活动周期天数

### 7.3 峰值评估

- QPS峰值 = 日均CMP交互量 / 86400 × 峰值倍数（通常3-5倍）
- 需与CMP侧确认承载能力
- 小米+海信月约1亿曝光，按1%抽样约100万/月，日均约3.3万请求被抽中

## 八、执行流程

```
1. 媒体播放广告，向秒针发送常规监测请求 + CF请求
2. 秒针CF服务收到请求，识别spid（和creative）
3. 查询该spid对应的抽样比例
4. 生成[0,1)随机数，判断是否 < 抽样比例
   ├─ 是 → 下发CF（含取帧秒数+桶偏移量）→ 媒体截屏取帧 → 本地提取HSV+pHash → 回传像素指纹
   └─ 否 → 不下发CF，正常走常规监测流程
5. 被抽中并成功回传的像素指纹数据 → 全量送CMP比对
6. CMP计算原始素材在相同CF下的期望值，双维度比对（HSV+pHash）
7. CMP返回比对结果
8. 秒针汇总输出报告
```

### 关键说明

- **抽样在CF下发环节执行**：未抽中的请求不触发像素监测，不产生像素指纹数据
- **被抽中并回传的数据全量送CMP**：没有二次抽样
- **常规监测不受影响**：无论是否被抽中，常规监测代码照常执行
- **未抽中的请求无像素日志**：8/19讨论的"全量日志留盘可回溯"优势不再适用，但常规监测数据全量在

## 九、报告影响

### 9.1 受影响的报告维度

- **画面对比不一致率（Y列）**：基于抽样样本计算，需标注抽样精度
- **像素方案相关指标**：基于抽样样本计算
- **常规监测维度（曝光量、UV等）**：基于全量常规监测数据，不受抽样影响
- **IVT相关（Z列）**：取决于IVT是常规监测的IVT还是像素方案的IVT——常规监测IVT不受影响，像素方案IVT基于抽样样本

### 9.2 小样本标注

- 单个spid×creative样本量<1000时，报告中标星号（*）提示精度较低
- 建议百分比和绝对数同时展示，降低理解门槛

### 9.3 抽检推回全体

- 抽样比例可推算总体，但**推算比例落不到具体日志**——未抽中的请求没有像素指纹数据，无法回溯标注
- **结论**：抽样仅用于CMP比对成本控制，不做日志级回溯标注
