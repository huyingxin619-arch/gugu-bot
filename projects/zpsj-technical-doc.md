## 一、方案概述

### 1.1 核心目标
验证广告播放时画面内容与原始素材一致，防止**替换、遮挡、静帧、黑屏**等作弊行为。

### 1.2 验证维度

| 维度 | 技术方案 | 作用 |
|------|---------|------|
| **色彩特征** | 24维HSV直方图 | 提取画面整体色彩分布，抗轻微画质压缩 |
| **空间结构** | 单帧pHash（DCT感知哈希） | 保留图像结构信息，识别画面内容是否一致 |
| **抗伪造** | 挑战因子动态分桶 | 防止媒体端预计算或伪造HSV值 |

### 1.3 双链路解耦架构（核心价值）

将**计费上报**（必须实时）与**视频验证**（可延后）从"串联依赖"改为**并行解耦**：

```
┌────────────────────────────────────────────────────┐
│                    媒体端                           │
├────────────────────────────────────────────────────┤
│  链路A（phsv=0）          链路B-1（phsv=1-1）       │
│  计费链路                 验证链路-帧1              │
│  ├─ 生成session_id       ├─ 请求挑战因子+采样时间戳  │
│  ├─ 上报曝光数据          ├─ 提取视频帧1            │
│  ├─ < 100ms完成           ├─ 计算HSV24 + pHash      │
│  └─ 参与GIVT+SIVT        ├─ 上报验证数据            │
│                           └─ 可重试，不参与IVT      │
│                                                     │
│                           链路B-2（phsv=1-2）       │
│                           验证链路-帧2              │
│                           （同上，第二帧独立上报）    │
└────────────────────────────────────────────────────┘
                           │
                    session_id 关联
                           ▼
┌────────────────────────────────────────────────────┐
│                    秒针端                           │
├────────────────────────────────────────────────────┤
│  1. 接收计费日志（phsv=0）→ 立即返回成功             │
│  2. 接收验证日志（phsv=1-1/1-2）→ 立即返回成功       │
│  3. 异步执行：                                       │
│     ├─ GIVT+SIVT验证（仅phsv=0）                    │
│     ├─ 若phsv=0被过滤 → phsv=1-1/1-2同步标记过滤    │
│     └─ HSV+pHash验证（未被过滤时执行）               │
│  4. 比对：媒体回传值 vs 秒针基准值                   │
│     ├─ pHash：必须完全一致                          │
│     └─ HSV：余弦相似度 ≥ 0.95                       │
└────────────────────────────────────────────────────┘
```

## 二、关键技术细节

### 2.1 HSV24直方图计算

- **分桶方式**：H(8桶) + S(8桶) + V(8桶) = 24维
- **抗伪造机制**：挑战因子(1-65535)参与H/S/V分桶边界的循环偏移
- **偏移逻辑**：
  - H_shift = (challenge_factor % 180) / 22.5 % 8
  - S_shift = (challenge_factor % 256) / 32 % 8
  - V_shift = S_shift

### 2.2 单帧pHash计算

1. RGB转灰度
2. resize到32×32
3. DCT变换
4. 取左上角8×8低频系数
5. 二值化（> mean = 1，否则 0）
6. 拼接为64位uint64

### 2.3 双采样时间戳策略

**仅支持15秒和30秒视频**（硬性限制）：

| 视频时长 | 采样点1 | 采样点2 | 最小间隔 |
|---------|--------|--------|---------|
| 15s | 7s | 12s | 5s |
| 30s | 15s | 25s | 10s |

> 动态调整：挑战因子参与随机化，确保采样点不固定，防预计算。

### 2.4 Session ID 关联机制

```
格式：{device_mac_md5}_{timestamp}_{material_id}

链路A(phsv=0) ──┐
                ├──→ session_id 唯一关联三条日志
链路B-1(phsv=1-1)┘
链路B-2(phsv=1-2)
```

## 三、数据上报与验证流程

### 3.1 媒体端需回传字段

**链路A（phsv=0）必要参数：**
- session_id, phsv=0, ad_creative_id, device_mac(MAC的32位大写MD5)

**链路B（phsv=1-1/1-2）必要参数：**
- session_id, phsv, ad_creative_id, sample_pts_ms
- ad_rendered_width/height, ad_type, device_model, ad_file_type
- histogram_counts（24个整数数组）
- frame_phash（uint64）
- challenge_factor

### 3.2 秒针端验证逻辑

```python
# 1. 挑战因子合法性校验（缓存24h）
# 2. pHash一致性校验：reported_phash == baseline_phash
# 3. HSV余弦相似度校验：similarity >= 0.95
# 4. 若phsv=0被GIVT/SIVT过滤 → phsv=1-1/1-2同步标记filtered
```

### 3.3 验证结果状态

| 状态 | 含义 |
|------|------|
| valid | 验证通过 |
| invalid | 验证不通过（HSV或pHash不匹配） |
| filtered | 被GIVT/SIVT过滤 |
| pending | 待验证 |

## 五、设计决策要点

### 5.1 为什么用单帧分别上报（而非双帧融合）？

| 维度 | 单帧上报（V2.0） | 双帧融合（旧版） |
|------|-----------------|-----------------|
| 计算复杂度 | 低 | 高 |
| 验证准确性 | 高（直接验单帧） | 中（融合可能失真） |
| 错误恢复 | 强（一帧失败不影响另一帧） | 弱 |
| 调试难度 | 低 | 高 |

### 5.2 为什么仅支持15s和30s？

文档未明确说明，推测为：
- OTT广告素材标准时长以15s/30s为主
- 采样策略（固定时间点）需要预设时长边界
- 可能为降低初期适配复杂度

### 5.3 为什么HSV阈值设0.95？

- 需经真实数据验证后调整
- 当前为保守阈值，兼顾画质压缩容忍度和作弊识别敏感度

## 六、错误码速查

| 错误码 | 说明 |
|-------|------|
| challenge_factor_not_found_or_expired | 挑战因子不存在或过期（24h） |
| frame_phash_mismatch_phsv_1-1/1-2 | 第1/2帧pHash与基准不匹配 |
| histogram_mismatch | HSV相似度低于0.95 |
| invalid_video_duration | 仅支持1000-300000ms，且实际只支持15s/30s |
| billing_data_not_found | 找不到关联的计费日志 |
