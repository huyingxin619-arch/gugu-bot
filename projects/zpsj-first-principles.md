# ZPSJ方案第一性原理分析 - HSV+pHash+挑战因子

> 从"为什么需要"倒推技术选型的必然性

---

## 一、根本问题回顾

**OTT广告验证的不可信假设：**

监测代码运行在OTT设备端（电视盒子/智能电视），而设备端是"黑箱"——广告主/秒针无法直接看到设备屏幕上实际播放了什么。

这意味着作弊者（不诚信的媒体/OTT厂商）可以：
1. **替换**：播放完全不同的素材（用户看到的不是宝洁的广告）
2. **遮挡**：在原素材上叠加蒙版、跳转按钮、其他广告
3. **静帧/黑屏**：播放了几秒后停止，画面定格或黑屏
4. **伪造数据**：根本不播放，直接在代码里生成假的特征值回传

> 传统元数据（流量、时长、设备ID）无法区分"播放了正确素材"和"播放了错误素材/伪造数据"。

因此，方案必须回答：**如何在不信任设备端的前提下，让设备端自证清白？**

## 二、为什么用HSV + pHash？

### 2.1 作弊攻击面分类

把作弊手段按"对画面改变的程度"分层：

| 攻击类型 | 改变程度 | 作弊动机 | 需要检测的能力 |
|---------|---------|---------|--------------|
| **完全替换素材** | 画面完全不同 | 播放更便宜的其他广告主素材 | 识别"这不是我买的那支广告" |
| **叠加蒙版/按钮** | 画面局部被覆盖 | 在广告主素材上叠加自家UI/跳转 | 识别"画面被篡改" |
| **压缩/转码/降码率** | 画质变化，内容不变 | 节省带宽 | 识别"内容本质上还是同一支"（避免误杀） |
| **伪造特征值** | 不上报真实画面 | 直接本地生成假数据 | 识别"数据是伪造的" |

### 2.2 单一特征的局限性

**只用pHash的问题：**
- pHash基于DCT感知哈希，本质是空间频率指纹
- 优点：对画质压缩鲁棒（同一画面压缩后hash大概率一致）
- 致命弱点：对**局部遮挡/叠加**极度敏感
  - 如果OTT厂商在广告上加一个"点击跳转"按钮（常见于电视广告），按钮覆盖了20%画面面积，pHash会从"匹配"变成"完全不匹配"
  - 但这在OTT场景里可能是**正常行为**（平台标准UI），不是作弊，不能误杀
- 另一个弱点：pHash只有0/1两种结果（匹配/不匹配），没有"相似度"概念，阈值调整空间小

**只用HSV的问题：**
- HSV直方图是全局统计量，描述画面整体的色彩分布
- 优点：对局部遮挡/叠加**极度容忍**（加一个小按钮不影响整体色彩分布）
- 致命弱点：对**内容替换**不敏感
  - 两支完全不同的广告（草原vs森林）可以有非常相近的HSV直方图，因为都是"蓝天绿地"
  - 如果仅看HSV，完全替换了素材也可能通过验证

### 2.3 组合使用的必然性

```
攻击面              HSV能检?    pHash能检?    组合后能检?
─────────────────────────────────────────────────────
完全替换素材           ✗           ✓           ✓
叠加蒙版/按钮          ✓           ✗（易误杀）    ✓
压缩/转码             ✓           ✓           ✓
伪造数据              ✗           ✗           ✗（需挑战因子）
```

**结论：单用任何一个都会留下大面积攻击盲区，组合使用才能覆盖主要作弊场景。**

### 2.4 HSV的额外优势：动态分桶

HSV直方图比pHash多一个关键属性：**它是数值向量**，不是0/1哈希。
- pHash是一个uint64整数，只能做"等于/不等于"判断
- HSV是24维整数数组，可以做**余弦相似度**计算
- 这意味着HSV有一个"灰色地带"：similarity=0.95通过，0.85不通过，有调节空间
- 而pHash只有"match/mismatch"，没有中间态

> 这也是为什么HSV阈值设0.95（可调），而pHash要求"完全一致"——因为两者数据结构的差异决定了它们适合不同的验证策略。

## 三、挑战因子的作用——为什么必须有？

### 3.1 没有挑战因子的问题

假设一个没有挑战因子的简化方案：

1. 秒针提前算好所有素材在所有可能时间点的HSV和pHash基准值
2. 设备端播放广告时，也在相应时间点算HSV和pHash
3. 设备端把算好的值回传给秒针
4. 秒针比对：回传值 == 基准值？

**这个方案的致命漏洞：设备端可以完全不播放广告，直接本地查表。**

作弊者可以：
1. 拿到素材库（广告素材是公开的）
2. 在自己的服务器上预计算所有素材在所有可能采样时间点的HSV和pHash
3. 存成一张大表：`{素材ID, 采样时间} → {HSV向量, pHash值}`
4. 等到要上报时，直接查表，不播放、不算、不提取帧
5. 回传的数据"完全正确"，但通过伪造而非真实播放

**本质问题：验证逻辑是"静态"的**——基准值固定，计算规则固定，所以预计算可行。

### 3.2 挑战因子的解法

挑战因子 = 服务端每次随机下发的**1-65535随机数**，参与HSV分桶边界计算。

具体怎么做：
- 标准HSV分桶边界固定（如H的8桶：[0, 22.5, 45, 67.5, 90...]）
- 挑战因子参与后，分桶边界发生**循环偏移**：
  - `H_shift = (challenge_factor % 180) / 22.5 % 8`
  - 原本第1桶[0-22.5)的像素，偏移后被分到第2桶
- 同一帧画面，在不同挑战因子下 → 完全不同的HSV直方图数值

**攻击面变化：**

| 攻击方式 | 无挑战因子 | 有挑战因子 |
|---------|----------|----------|
| 预计算查表 | ✅ 可行（一张表搞定） | ❌ 不可行（65535种组合，查表爆炸） |
| 伪造HSV值 | 知道规则就能伪造正确的固定值 | 不知道随机因子，无法伪造动态偏移后的值 |
| pHash伪造 | 同上 | pHash不受挑战因子影响，需配合服务端动态下发采样时间戳 |

> **挑战因子本质上把"静态验证"变成了"动态挑战-响应"**——就像密码学里的challenge-response协议，每次验证都是一次新的随机挑战，防止重放攻击和预计算。

### 3.3 为什么挑战因子只影响HSV，不影响pHash？

因为pHash是**确定性算法**（固定流程：灰度→resize→DCT→二值化），如果不改源码，pHash值不受外部参数影响。

方案用**双采样时间戳**来防pHash预计算：
- 服务端随机下发采样时间点（而不是固定7s/12s）
- 作弊者不知道要采样哪一帧，无法预计算所有帧的pHash
- 视频帧数可能成千上万，全部预计算存储不现实

> HSV用**挑战因子**防预计算，pHash用**随机采样时间戳**防预计算——两者互补，覆盖全部攻击面。

## 四、第一性原理总结

```
根本矛盾：设备端不可信，但需要设备端证明"我播放了正确的广告"
    ↓
解决思路：让设备端提交"画面特征指纹"，服务端交叉验证
    ↓
指纹选择：
    - HSV（全局色彩统计）→ 对局部遮挡鲁棒，防"加蒙版被误杀"
    - pHash（空间结构哈希）→ 对内容替换敏感，防"完全替换素材"
    - 两者互补，覆盖主要攻击面
    ↓
防止伪造：
    - 挑战因子 → 让HSV计算结果每次随机变化，防预计算/查表
    - 随机采样时间戳 → 让pHash采样点不可预测，防预计算
    - 两者组合 → 将"静态验证"升级为"动态挑战-响应"
```

## 五、仍待验证的问题

1. **15s/30s限制**是MVP临时还是长期 specs？如果客户要支持其他时长，采样策略如何调整？
2. **HSV阈值0.95**是否有真实数据支撑？误杀率和漏检率未知。
3. **pHash对蒙版的容忍度**：如果OTT平台在广告上加一个半透明跳转按钮，pHash是否会触发 mismatch？这个在O'TT场景下的误杀风险需要实际测试。
4. **设备性能差异**：方案宣称单帧≤50ms，但低端OTT设备的实际表现如何？
